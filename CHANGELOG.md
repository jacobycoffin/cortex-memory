# Changelog

## Unreleased

- added **bulk approve that only fires when a batch is provably the same as deciding each item** (`cli.py`): reviewing 340 proposals one at a time is how a queue ends up expired instead of decided, but a `--kind` shortcut is dishonest unless the items really do describe one change. So the command proves it first: **the kind must have a single absolute effect** (`edge_downscale` only - an `association` approval picks a relation from the operator's reason and a `lifecycle` approval picks a new state, so batching those would record a guess as the operator's choice); **every target must be an absolute `next_weight`** (a relative factor cannot be replayed safely); **every connection must still exist**; **no two proposals may name different targets for one connection**, because then order decides the result; and **all targets must be uniform**, otherwise the batch is several different changes wearing one label. Any failure refuses the whole batch with counts and the offending ids, and writes nothing. `--apply` is required to write - the default is a preview of exactly what would change - and after writing the command **re-reads every connection and reports any that did not land on the target**, so a partial batch cannot report success. On the live queue it previewed *250 proposals over 249 connections, every one to weight 0.05, one pair duplicated with the same target* and correctly identified that pair as idempotent. `tests/test_cli_proposals.py` covers eight paths including each refusal.
- fixed **`procedures` read as absent when the grading loop had never been deployed** (`rust/crates/cortex-store`, `rust/crates/cortex-cli`): `status --json` reported `procedures: {total: null, graded: null}` and `health.note: "not measurable yet"`, which is truthful about the *grading* table and misleading about the library - the live box holds **246 active procedure memories** and no `procedure_outcomes` table at all, so the honest reading looked identical to "there are no procedures". `procedures.known` now counts procedure memories (`kind='procedure'` and `state='active'`) independently of grading, and when the library is populated but nothing grades it the note says so: *"procedures are stored but none has been graded yet"*. The count is read-only and schema-agnostic (a store without a `memories` table reports not-present, not zero), `total`/`graded` are unchanged so the contract stays additive, and `status_reports_stored_procedures_when_nothing_grades_them` pins the populated-but-ungraded case.
- fixed **the dream's proposals expired unseen** (`cli.py`, `plain_summary.py`): the nightly cycle writes Sleep proposals into `sleep_proposals` and stops, and the only surface that could decide one was the dashboard - which nobody had running. So the queue accumulated untouched until `cortex_sleep_retention.py` swept it: **1,829 proposals expired between July and September 2026 with zero decisions**, which is the same failure as 277 procedures nobody grades - a mechanism that runs and whose output is never read. `cortex-memory proposals` is the missing surface: `list` (read-only, grouped by kind, with the rationale and the two memories), `approve` / `skip`, `undo <review_id>`, and `--json` for a headless caller. Decisions go through the store's existing `decide_review_proposal`, so the per-kind rules are unchanged and every decision is undoable. Two deliberate refusals: **a bare `approve` cannot archive or trash a memory** - `lifecycle`, `consolidation`, `dependency_repair` and `context_review` proposals require `--action archive|trash|quarantine|keep`, because "approve" is not shorthand for deleting something, while `skip` on those kinds means `keep` (protect, change nothing); and an ambiguous id prefix is refused rather than guessed. `cortex-memory status` now carries `waiting for review` and `expired unreviewed`, so a queue that is filling and a retention sweep that has been running are both visible without opening anything, and expiry reads as *"they timed out without a decision"* rather than as a clean zero. The window compares `substr(created_at,1,10)` against `date('now', ...)`: `created_at` is ISO text, and an ISO `T` sorts above a space, so the obvious `created_at >= datetime('now', ...)` comparison silently counts rows from any month. `tests/test_cli_proposals.py` pins all fifteen paths.

- added **short-form embedding view** (`store.py`, `scripts/backfill_short_embeddings.py`): memories are long (median ~19 tokens, p90 82) and real queries are short (median 7), so one vector per memory over full content cannot place many of the memories that were actually used inside a 200-wide candidate cut. Each memory now also carries a vector over its **short form** - the presentation's `display_title` + `display_summary` from `memory_presentations`, falling back to the full content when a memory has no presentation - stored in the same `memory_embeddings` table under the view-discriminated key `f"{model_id}#short"`, so no migration is needed and every existing reader (which asks for the bare model id) is untouched. `set_memory_embedding(..., short_vector=...)` writes both views in one transaction, `set_short_form_embedding` fills only the second view, and `short_form_texts` is the single place the indexed text is composed (an identical title/summary is not embedded twice). `semantic_top_ids_merged` returns one pool across both views: deduped by memory id, keeping the **best** similarity, re-sorted, so a memory found twice appears once. Nothing here commits on its own - embedding writes join the caller's transaction - and `retrieval.py` is deliberately untouched: the merged query is exposed for it to consume separately. `scripts/backfill_short_embeddings.py` fills the missing second view for the existing corpus with the same memory gate, small batches and resumability as the full-text backfill, and writes only short vectors. The matrix cache now holds a few views instead of one slot, because a merged query alternates between the two keys and a single slot would rebuild both each call.
- added **two plain-language CLI commands** (`plain_summary.py`): `cortex-memory status` and `cortex-memory why <id>`, because the surfaces that existed (dashboard, phone page, private scripts) answered *what is in here* and nobody answered the two questions a person actually asks. `status` prints five short lines - memories stored, memories recalled in the last 7 days, answers graded, procedures graded, last recall - and prints `not measurable yet` wherever the store holds no record, because a missing table means the instrument never ran and an empty table means it ran and found nothing, and printing `0` for both is how an unfed mechanism reads as a healthy store. `why` explains one memory in plain sentences: what it is and where it came from, when it was last recalled, whether it was ever credited in an answer, and - when `recall_score_breakdown` holds one - the rank it got and the signals behind it under plain names (`semantic_fusion` reads as "found by meaning", never as a key dump). Both open the database `mode=ro`: no command can create a schema, migrate, or write a row, and a `--db` typo prints "no Cortex database at ... yet" instead of manufacturing an empty store that reads as a working one. A missing table, an empty store, an unknown id and a path that does not exist each produce a sentence and a clean exit, and `tests/test_cli_plain_language.py` pins all four paths.
- added **per-stage recall timing you can report from the store** (`recall_timing.py`): the live measurement this closes was a first prefetch of **1,422 ms** against a **1,500 ms** pre-turn deadline, then 1,142 / 726 ms warm - about **800 ms of the first turn was the one-time ONNX model load**, and nothing in the store could say so. Three gaps, three fixes: **the load is its own stage** (`embed_load`, plus `embed` for the whole embedding call, published by `Embedder.last_load_ms`/`last_embed_ms` and written by the semantic stage); **rendering is timed** (`render`, around block composition in the prefetch path); and **a value in `stage_ms` is a duration only if `STAGE_DURATIONS` says so** - counters now carry the required `_count` suffix (`reranked`, `authority_capped`, `duplicates_replaced`, `namespace_blocked`, `density_selected`, `superseded_demoted`, `stability_boosted`, `entities_anchored`, `negative_cue_suppressed`), so a report can no longer rank "abstained: 1.0 ms" as a pipeline stage. `stage_percentiles(store, window=...)` returns p50/p95/p99 per stage plus counters kept apart, **excludes cached runs** (they stored `0.0` for every stage they never ran, which dragged the p50 toward a latency nobody measured), and `format_report()` prints it. Storage is unchanged: `recall_runs.stage_ms_json` already existed and is keyed by `task_id` like `recall_budget_observations`, so no second table was needed. **Instrumentation is now total** - `StageSink`, `clock()`, `elapsed_ms()`, the store's `sanitize_stage_ms()` boundary and the latency budget all degrade to a dropped measurement instead of an exception, because a timer must never be able to cost a recall; `tests/test_recall_timing.py` proves it by patching `time.perf_counter` to raise and still asserting memories come back.
- fixed **every `plugins.cortex` setting was silently ignored when no YAML library was importable** (`hermes_config.py`): `_load_yaml` tried PyYAML, fell back to ruamel, and `_read_config` caught the resulting `ImportError` and returned `{}`. The Hermes runtime ships **neither** library (`include-system-site-packages = false`, and the 3.14 runtime's site-packages has no yaml), so the provider fell through to its defaults - which is how a profile opened an *empty* store while the real corpus sat at the canonical path, and how a corrected `db_path` appeared to do nothing. `_read_config` now falls back to `_read_cortex_block`, a deliberately narrow reader for this one setting: two levels of mapping, scalars only, nested containers skipped rather than guessed at, quote-aware so a `#` inside quotes stays content. Verified against the real 13,948-byte profile config **in an interpreter with no YAML library**: 9 keys, `db_path` and `shared_db_path` correct, booleans and ints coerced. Note the first version of that reader stripped comments before unquoting, which truncated a quoted value at its `#` - the test caught it.
- fixed **the automatic admission bar was unreachable by its own rules** (`store.py`): a candidate is admitted automatically only above a bar, and the *temporary* bar was `0.62` - but `volatility >= 0.70` is both what makes a candidate temporary **and** a `0.12 * (1 - 0.70) = 0.036` deduction, while `operational` carries the lowest type prior. The two rules cancelled: operational candidates topped out at 0.60-0.62 and were always refused. Measured on a live profile: **52 of 52 automatic writes refused**, several at `0.6012` and `0.6192` - facts like *the queue console runs on port 8791* - and its memory store therefore stayed at **0 rows** while the write ledger advanced daily. The bars are now named constants (`MANUAL_MIN_REUSABLE_SCORE` 0.45, `AUTOMATIC_MIN_REUSABLE_SCORE_DURABLE` 0.52, `AUTOMATIC_MIN_REUSABLE_SCORE_TEMPORARY` 0.58) and the assessment reports the bar it applied as `minimum_reusable_score`, so the gate is inspectable instead of implied; a bar that cannot be reached fails silently, because "ignored" looks exactly like "nothing to store". The lower bar does not make the gate a rubber stamp: `tests/test_admission_bar.py` pins that a weak candidate is still refused, that the temporary bar stays above the durable one, and that a manual write keeps the lowest bar.
- added **failure-mode memory** (`failure_modes.py`, #133): `handoff_notes` keeps typed advice per tool and `argument_memory` keeps which argv failed, but neither answers the question that costs the most time - *this exact thing fails on this exact host, and here is what to do instead*. A mode is context + signal + workaround. Six rules: **a failure is bound to its context** (a mode with no context is refused at write time, because "it failed" is a complaint, not knowledge); **the signal is kept so it can be matched again, redacted on the way in** (so the catalogue cannot become a secret store - `Authorization: Bearer <token>` needed its own rule, since the credential sits after the word rather than after a colon); **a workaround is what makes it advice** (no workaround means `unexplained`: worth knowing, never offered); **recurrence is counted**; **a later success resolves the mode** - kept, not deleted, so the history stays readable while the advice stops being offered, and **a recurrence reopens it**; and **resolved modes are never offered**. A store that has never recorded anything is an empty catalogue, not a broken one.
- added **tool preference per task** (`tool_preference.py`, #132): the store records outcomes and gates them, but nobody could ask the question a person actually asks - *for this kind of task, which tool should I reach for?* A preference is a procedure whose id is `task::tool`, so the outcome history, the consecutive-success gate and the failure evidence come from `procedure_confidence` (#142) and `procedure_validation` (#115) instead of a fourth ledger. Rules: **a preference is earned here, not assumed** (no defaults, no model priors - a tool is preferred because this store watched it work); **only validated tools are offered**; **a tool that fails more than it succeeds is never preferred, even when it is the only candidate**, because "the only tool ever tried" is not a recommendation; **the count travels with the preference**; **a tie returns nothing** (a coin flip dressed as guidance is worse than silence); and **reading only** - it recommends, the caller decides, nothing here runs a tool. The tool keeps its exact shape, so `pytest -n 2` and `pytest -n 8` are different tools with different records.
- added **procedure validation** (`procedure_validation.py`, #115): `procedure_confidence` (#142) says how much a procedure is trusted and `argument_memory` (#134) keeps the failures, but neither **gates** anything - a procedure with one lucky run was as available as one earned over a month. A procedure is now **offered** only after **three consecutive successes**; everything else is withheld with the count and the reason. Six rules: **consecutive successes, not a total** (a procedure that worked three times and then failed is not validated - the failure is the newer evidence, and summing lets a broken procedure inherit its own history); **N is stated in every verdict** ("withheld, 2 of 3" reads as progress, "withheld" alone reads as breakage); **no evidence is its own verdict** (`unvalidated`), never silently offered and never broken; **the last failure travels with the verdict** because that is the actionable part; **reading never creates schema** (a store that has never recorded a run has no table, and that is not an error - it took a fix in this module to stop reporting `unreadable` for `unvalidated`); and **the gate is a read** - it decides what may be offered and never retires anything.
- added **cross-domain transfer** (`cross_domain.py`, #113): `cross_project.py` (#78) bridges a query to another project's memories while answering; this is the other half - at consolidation time, notice that two projects are shaped alike and that one holds a pattern the other lacks, then **propose** the transfer. A pattern is a structured memory's `(predicate, object_value)` counted per project; free text has no pattern and pretending it does turns this into a similarity search with a story attached, so unstructured rows are skipped **and counted**. Six rules: **a transfer is a proposal, never a write** (the pattern was established in another project's context, and asserting it here is a person's decision); **the likening is stated** with the shared patterns and a Jaccard score, because a proposal whose evidence is invisible cannot be audited; **a pattern the target already holds is not proposed** - that is duplication, not transfer; **evidence on both sides** (source memories and the shared patterns); **thresholds are printed in the output** so a quiet night reads as 'nothing crossed the bar' rather than 'the feature is broken'; and **proposals are deduplicated per run**, because the same suggestion twenty times is noise. Proposals land in `sleep_proposals` as `cross_domain_transfer` against a run id, and never become memories.
- added **consolidation rollback** (`consolidation_rollback.py`, #112): a night of consolidation can merge a dozen memories and the only way back was one `merge_diff.undo(merge_id)` at a time - knowing the ids, in the right order, hoping nothing else moved. This reverses the whole night and refuses the parts that are no longer safe. Six rules: **reverse order, always** (merges in a night form a chain, so undoing forwards restores a row into a state a later merge already changed); **a survivor edited after the merge is not rolled back** - the undo record restores the pre-merge row, so reversing would silently discard that edit, and the refusal names the field; **stop at the first failure**, because the remaining undos were planned against a state the failure just disproved; **already-undone is reported, not retried**, so the command can run twice; **the night uses the same 06:00 UTC boundary** as the budget and the journal; and **dry run by default with a named consent**, with the reversal leaving its own record - a reversal nobody can see is indistinguishable from a merge that never happened. One fix was needed underneath it: `merge_diff` recorded only the pre-merge state, so nothing could tell "the survivor still looks like the merge left it" from "somebody edited it afterwards"; it now reads the survivor back inside the merge transaction and stores the after-state, which is the only thing that makes a safe rollback possible. **Live on a copy: the store holds **0 merge records** - the rollback is complete and unexercised, because nothing has ever merged through `merge_diff`: it is a review tool the sleep cycle does not call, so the finding is not that the rollback fails but that there is no consolidation for it to reverse**;
- added **summary regeneration** (`summary_regen.py`, #109): `generate_summary_candidates` records a signature over the two memory **ids** plus an excerpt of each source's text - enough to create a summary and not enough to maintain one, because an edit leaves the ids unchanged, `INSERT OR IGNORE` sees a duplicate, and the summary keeps asserting the old text forever. This module notices. Five rules: **staleness is about facts, not age** (a summary of unchanged facts does not decay; a summary of an edited fact is wrong the moment the edit lands, however new it is); **the reason travels with the finding** and names the sources, because `source_changed` and `source_retired` are different decisions for a reviewer; **supersede, never delete** - a retired candidate keeps its claims and sources, since what the store used to believe is evidence; **regeneration proposes and never promotes** (a refreshed summary re-enters the same review path, nothing here creates recallable memory); and **planning writes nothing**, applying needs explicit consent. It needs no schema change: the recorded excerpt is already the snapshot that drift is measured against. **Live on a copy: of 269 proposed candidates, **92 are stale (34%)** - 55 because a cited source was retired, 35 because a cited source's text changed, 2 for both; 65 individual sources retired and 41 changed; 177 current, scanned in well under a second**;
- added **interference pruning** (`interference_pruning.py`, #108): two memories can interfere in exactly two ways - they say the same thing, in which case one is noise and the store can decide, or they say different things about the same subject, in which case only a person can. The whole design is that distinction: **exact duplicates may be settled in batch, contradictions may not** (they are queued with their reason and left alone); **only exact duplicates are automatic**; **a merge that would lose a fact or structure is never automatic**; **dry run by default** with consent required to apply; and **bounded, with the skips counted**. The heavy lifting is not re-implemented - consequences come from `merge_diff.compute`, contradictions from `contradiction_cluster` - this module decides what may happen without a human. **Live on a copy: 3,831 active rows, **0 exact duplicate groups** (the write path already dedupes exact content, so this module mainly sees imported and legacy rows), and **18 near-duplicate pairs at 0.85-0.99 overlap** that need a decision, from a complete scan of 95,221 candidate pairs in 17 s - the count read 16 while the scan was capped at 50,000, which is why the cap now finishes the work instead of silently lowering the number of findings**;
- added **procedure handoff notes** (`handoff_notes.py`, #143): a procedure that worked yesterday can fail today for a reason nobody wrote down - the machine suspends when its owner walks away, a conflicted PR shows no checks, an inhibit call needs interactive auth over SSH - and the next session re-learns each by hitting it. Five rules: **a note has a kind** (`last_failure`, `precondition`, `gotcha`, `env`) because the four are read differently and an untyped note is a sentence nobody can act on; **a note is bound to the tool shape it was written against** (the same pair as #138) so a shape change marks it `stale` rather than letting it mislead; **the newest failure outranks old advice** when the handoff is cut; **the handoff is bounded by construction, not by truncation** - one note per kind means at most four lines, and a lower limit states what it left out; and **notes are superseded, never deleted**, with `superseded` (history) and `stale` (the tool moved) as different marks because they are different facts. **Live on a copy with this session's own handoff for `verify-branch-on-mac`: four notes in priority order (polkit refused the inhibit; confirm tailscale shows the runner online; a suspended laptop kills the run mid-suite; the venv lives in the main checkout not a worktree), the kernel-shape change marking exactly one note stale, and an unnoted procedure saying so**;
- added **procedural confidence** (`procedure_confidence.py`, #142): a procedure is a claim that doing X gets you Y, and treating forty clean runs the same as one untried recipe is how a store of procedures rots. `confidence = smoothed_success x evidence x recency_decay` - Laplace-smoothed so one lucky run is not 100%, **failures weighted 1.5x** because a failure says the procedure is wrong *somewhere* while a success only says it worked that time, evidence capped below four outcomes, and a 45-day half-life on idleness. Five rules: **retrieval is not evidence** (reading or injecting a procedure never raises it - the same discipline as 'a memory never becomes true by being retrieved'); **the number never travels alone** (successes, failures and idle days are printed beside it); **a failed run is recorded as a failure, not as silence**; **decay is a function of idleness, not wall time**; and **the same outcome at the same moment is idempotent**. An absent table reads as `untested`, not `unreadable`. **Live on a copy with this environment's real history: `verify-branch-on-mac` 0.86 trusted (14 ok, 1 failed); `merge-when-all-green` 0.61 trusted (3 ok, 1 failed - the time I merged with 3.14 pending); `sync-main-before-merge` 0.52 learning (4 ok, 0 failed, but 30 days idle, so decay is visible); `sleep-inhibit-over-ssh` 0.10 suspect (0 ok, 2 failed)**;
- added **tool deprecation tracking** (`tool_deprecation.py`, #138): a procedure is only as good as the tool it was written against - `t3` 0.0.45 speaks V1 and quietly lies about a V2 store, Omarchy moved its bar from Waybar to Quickshell, a CLI renames `--json` and every recipe that used it becomes a guess - and nothing in a store of procedures notices. Six rules: **invalidation demotes, never deletes** (a stale procedure is still evidence of intent); **invalidation is per tool** (a `gh` change must not taint a `pytest` recipe - over-broad invalidation trains people to ignore the flag); **the previous shape is kept** for a rollback, though a rollback re-validates nothing by itself; **a procedure with no recorded shape is `unpinned`, not current**; **re-verification is an explicit act requiring evidence** (what did you run, what did it say); and **observing the same shape twice is a heartbeat, not a change**. Reading never creates schema: no tables means 'nothing observed', which is not 'could not read'. **Live on a copy with real shapes: `t3` 0.0.45 -> 0.1.4 demoted two procedures (`t3-thread-show`, `t3-serve-127`); `omarchy-bar` waybar -> quickshell demoted the bar-module procedure - the exact trap this session hit when the box turned out to run Quickshell, not Waybar; `pytest` was untouched by both, one procedure stayed `unpinned`, revalidation returned `current` with evidence and was refused without it, and a repeated `pytest 9.2` observation changed nothing**;
- added **argument memory** (`argument_memory.py`, #134): some invocations are learned the hard way and then forgotten - `pytest -n 4` is the sweet spot while `-n 8` buys nothing, `systemd-inhibit --mode=block` works in the desktop session and is refused over SSH, `git worktree remove --force` discards uncommitted work. Six rules: **failures are kept** (an argv that fails is worth more than one that works, especially when it fails slowly); **the invocation is stored as data** (command + argv list) so it replays verbatim instead of being re-parsed; **a later success does not erase an earlier failure** - the same argv with both outcomes is reported as `mixed` with counts, because that means the result depends on context and must not be settled by whoever wrote last; **recall never recommends a known-bad argv**; **no secret ever reaches the table** - a key, bearer token, named secret flag or 40+ character opaque value is refused at the door and the refusal names the pattern, never the value; and **recording is idempotent**. Reading never creates schema: a store with no table answers 'nothing recorded', which is not the same as 'could not read'. **Live on a copy, seeded with what this session actually learned: `pytest` recalls `tests/ -q -n 4` (21 s on the MacBook, 982 s on the VPS) alongside `-n 8` with the note that it buys nothing; `systemd-inhibit --what=sleep:idle --mode=block` comes back `mixed` - works locally, polkit refuses it over SSH; `git worktree remove --force` and `gh pr checks <n>` on a CONFLICTING PR both come back as known failures with their reasons; and a bearer token was refused without being echoed**;
- added **model choice for the night** (`model_choice.py`, #118): sleep reflection is the one place the store spends real money on real reasoning, and it is wired to three env vars somebody must set by hand - measured on the live store it has run **0 times in 82 sleep runs**, every one recorded `disabled`, so the item's premise ('sleep uses the strongest available model, not the chat model') was true in neither direction. The resolver walks a **declared ladder** (`sleep_explicit` -> `judge` -> `mechanics`, each naming the env vars that configure it), **checks availability rather than assuming it** (a tier is usable only when model, endpoint and key are all present; the skip reason names the variable, never its value), **never inherits the chat model**, treats an **explicit pin as authoritative** (missing key -> `refused`, never a silent downgrade) while an **ambient `CORTEX_SLEEP_MODEL` falls back loudly**, and returns `usable=False` with the full list of what it looked for rather than inventing a default. It resolves and reports - it spends nothing and switches nothing on. **Live: with `sleep.env` alone the answer is 'no tier is usable' (that file configures only the token budget); with the deployment's `auto-judge.env` declarations the ladder resolves to `judge: deepseek-flash` via `api.deepseek.com` with key variable `DEEPSEEK_API_KEY`, `fell_back=True` because no sleep-specific model is configured - i.e. the model this store would actually think with at night is deepseek-flash, not the chat model, and the fallback is now visible instead of implicit**;
- added **backlog-aware scheduling** (`sleep_priority.py`, #117): `sleep_budget` answers *may I start another unit*, this answers **which** one - and the difference only matters when the budget runs out, which is exactly when a scheduler walking a fixed list looks busy while doing the least valuable third of the job. Five constraints: **cost is measured or marked unmeasured** (a kind whose unit cost nobody measured is placed last and labelled, never given a made-up number - a guess wearing a decimal point is worse than an admission); **value is a declared number in (0,1]** printed with every decision; **a unit that does not fit is skipped, never truncated** (half a replay unit is a half-written trace); **every task carries the module that owns it**, so the scheduler cannot invent work it cannot hand off; and **the order is deterministic**. `measured_from()` takes the **median** of observed costs, not the mean, so one 12-second outlier does not set the price. **Live on a copy, and the finding is that the ranking has one entry: the store measures replay (median 971 ms over 4,724 runs) and nothing else - 200 replay units are 194 s of a 600 s budget, so at the real ceiling the order changes nothing and the feature only bites below ~200 s; at 60 s, 61 units fit and 139 are skipped with the arithmetic in the reason, and `near_duplicate_merge` (value 0.9) and `digest` sort last as unmeasured despite being more valuable than everything measured**;
- added the **entity hygiene score** (`entity_hygiene.py`, #116): a store can be large and still tell you nothing useful about the things you talk about - one glancing mention, two statements that disagree and both still say `active` - and no per-memory score finds them, because the problem is the entity, not any one row. The score is boring on purpose (`1.0 - 0.35*contradictory - 0.25*thin - 0.15*stale - 0.10*unexercised`) and **never travels without its parts**; a retired side is history rather than a contradiction (counting it would punish the store for having been corrected); thin is reported apart from bad because a new entity is thin for a week and that is correct; only active/cold rows count; and an entity with no memories is not scored at all. **Live on a copy, and the finding is the input rather than the score: 2,659 entities - 2,054 thin, 323 healthy, 282 unexercised, **0 stale, 0 contradictory** - because `entities_json` is populated with **vault note headings** (2,145 of 2,659 contain `›` or `.md`, e.g. `Slskd (Soulseek) › Status: 🟢 plateaued - 106/153 downloaded`), and there is no entity table at all (`entity_aliases` is empty, `entity_nodes` does not exist). Across 7,502 structured memories there are **0 conflicting (entity, subject, predicate) groups**, so the contradiction term is inert for the same reason the replay regret term was: the field it reads is not populated with what it means. The score is correct and will grade real entities once something extracts them; today it grades section titles**;
- added the **dream journal** (`sleep_journal.py`, #111): most of what a night finds, it should not act on - a near-duplicate that is not close enough, a contradiction whose sides are both cited, a memory nothing can classify - and today each of those is dropped silently, so the cycle looks clean in the morning because its doubts were never written down and the same near-misses are re-discovered nightly. Five rules: **a notice is not an action** (writing one changes no memory; a snapshot test enforces it, because restraint must not quietly become a queue); **every entry says why it was not acted on** from a closed set (`below_evidence_bar`, `contradicted`, `budget`, `needs_decision`, `not_scheduled`) - free text cannot be counted, and the count is what says whether a bar is set wrong; **per night, deduplicated** (the same ids in a different order are the same notice, and repeats increment `times`); **bounded, and the bound refuses rather than truncates**, telling the caller to aggregate; and **it keeps ids, not content**, because a journal that quotes memories is a second copy of the store with weaker rules. **Live on a copy: the first real night fills the journal to 40 and the 37th `not_scheduled` entry is refused with 'aggregate instead' - 3 near-duplicates below the bar, 1 aggregate (3,817 active memories with no sensitive-domain class), and 36 stale samples - which is exactly why the cap has to exist: the store has 3,828 replayable candidates and a journal that wrote one line each would be the second store it is trying not to be**;
